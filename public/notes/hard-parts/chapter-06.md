# Chapter 6: Pulling Apart Operational Data

Database decomposition is an architectural boundary change with unusually high stakes. Data is a business asset, and its coupling is often hidden in foreign keys, views, triggers, and stored procedures. The chapter therefore starts with a justification question: what evidence says that a monolithic database is now hurting the system? The six disintegration drivers are change control, connection management, scalability, fault tolerance, architectural quanta, and database type optimization (text lines 3600–3618).

Change control is often the clearest driver. A dropped column or changed type can break every service that queries a shared table, and forgotten consumers fail in production (text lines 3630–3655). A bounded context limits that blast radius. The owning service can translate database fields into a stable contract, so an internal schema change does not automatically become a consumer change (text lines 3660–3704). Ownership here means writing data; a read-only caller should use a contract rather than query another context directly.

Connection management and scaling expose a different failure mode. Each service instance normally owns a connection pool, so distribution can multiply demand before traffic rises. The book’s example grows from 200 connections in a monolith to 1,000 across 50 services, then to 1,700 as instances scale (text lines 3706–3740). Quotas govern the shared pool. Equal quotas are a practical starting point; streamed measurements of maximum use and waits can then support variable quotas (text lines 3742–3910). Crucially, quotas must be checked against instance counts: a nominal 100-connection allocation can become 242 connections after scale-out (text lines 3920–3998).

Fault tolerance and architectural quanta ask whether a shared database makes unrelated functionality fail together. If it is down, every connected service is down. Separate data can leave one domain operating while another is unavailable (text lines 3996–4024). Database type optimization adds a workload question: relational, key-value, document, graph, column-family, NewSQL, cloud-native, and time-series systems have different strengths (text lines 4409–4790).

Two integrators temper the case for splitting. Relationships and transactions may be more valuable than independent deployment. Local foreign keys can remain, but cross-domain artifacts must be removed or replaced (text lines 4048–4108). Similarly, a single ACID unit disappears when writes cross databases; partial commits require another consistency strategy (text lines 4062–4070). The five step process makes this migration evolutionary: define domains, assign tables, remove cross-domain artifacts, move services to domain schemas, and finally separate physical stores (text lines 4116–4408).

Teaching extension: choose one real schema and draw its data domains. For each proposed boundary, record one measured disintegrator, one relationship or transaction integrator, and the first reversible migration slice. Do not claim that a technology choice solves a boundary problem; first show who owns each write and how a caller receives foreign data.

The chapter’s negotiation with Dana is itself instructive. The database team owns operational knowledge and must participate in the boundary decision; a decomposition plan that ignores that expertise is not an executable architecture (text lines 3575–3600). Treat the migration as collaboration between application, architecture, and database roles. A domain diagram is a hypothesis until queries, ownership, and deployment dependencies confirm it. Fitness functions for connection waits, failed calls, migration lag, and schema impact make the hypothesis testable.
